## 1. Project layout

- A flow root is a directory that contains a `main.rein` file. A flow is a flow root found through scopes (section 1a), or a directory passed to a command. A program can also be one `.rein` file: its folder is the flow root and its name is the entry (section 1a).
- Each function is one file with the `.rein` extension.
- A shared struct is one file named `<name>.struct.rein` (section 4, Structs). It is not a function. `rein graph`, the reachability warning, and workspace symbols as functions leave it out. `rein show` prints it.
- Every flow root has a `main.rein`. It is the agent's entry point. The checker reports a flow root without it. A program run from its own entry file needs none (section 1a).
- A function name is the file path relative to the flow root, without `.rein`, using `/` as separator. `ci/fix.rein` defines `ci/fix`. The root `main.rein` defines `main`.
- The name of the `export default function` inside a file is a TypeScript identifier. It need not match the file name.
- Subdirectories are allowed.
- A function that exactly one other function calls lives in a folder named after that caller, next to the caller's file. The only caller `<dir>/<name>.rein` puts the callee at `<dir>/<name>/<callee>.rein`. `merge.rein` is the only caller of `fix_ci.rein`, so the file is `merge/fix_ci.rein`. Then the folder structure shows the program.
- The entry function (`main`, or `entry` in `rein.json`) is the exception. The program root already is its folder, so a function that only the entry calls stays next to it at the root.
- A function with two or more callers is shared. It stays where it is. No rule puts it in a place yet. A later rule can put it at the nearest common folder of its callers.
- The rule does not cover std items, `.struct.rein` files (a struct is not a function), functions with no caller or not reachable from the entry (the reachability warning covers them), or references to other programs.
- A function whose target path another file already has gets no warning, because it cannot move there. When two functions have the same target, such as `x/leaf` and `y/leaf` with the one caller `a`, each warning names the other and has no quick fix. Rename one of them first.
- A function whose only caller sits in the function's own folder, such as `x` called only by `x/y`, gets no warning. The caller would move with it, so the function could never reach the caller's folder. The same holds when the function's folder holds the entry, such as `app` with the entry `app/start`: the entry would move and `rein.json` would name a file that is gone. A rename or move that would carry the entry along is refused.
- The root `main` never gets the warning: the project needs it, and a `main.rein` below the root makes its folder another flow. A target path that runs through a folder the loader skips (a hidden folder, `target`, `node_modules`, or a folder with its own `main.rein`) gives no warning, and a rename or move into such a path, or one that puts a `main` below the root, is refused. The function would drop out of the program.
- A function in the wrong place is a warning that names the target path. The language server has a quick fix, `Move to <path>`, that moves the file and rewrites every reference to it and every relative reference inside it. The folder of functions nested under it (`<name>/`) moves with it, so they stay in place. A rename of a function also renames that folder. A callee keeps its file name when it moves. A rename, move or quick fix is refused, with the reason, when the function's folder (`<name>/`) or a folder inside it holds a file that is not a `.rein` file of the project (such as `notes.md`) or a folder the loader skips or a folder with its own `main.rein`; or when the folder or anything inside it is a symbolic link, whether it points to a file or to a folder. The symlink check covers the function's folder and everything inside it, files and folders alike. It does not cover the ancestor folders of the function, or the destination path. Hidden files and editor and OS leftovers (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `*.swp`, `*.swo`, `*~`) do not block a move. They are renamed with the folder, so they land in the new folder. A relative reference that does not resolve keeps its target, in a moved file or in a file that stays put. The move is refused only when that reference would then resolve to a function or shared struct, such as `@../c` in `a/b` when a rename of `a` to `c` creates `c.rein`, or `@./c` in `x` at the root, which stays put. A reference that leaves the project root, such as `@../../nope`, is treated the same way: it blocks the move only when, written from the moved file's new folder, it would name a file. On a case-insensitive file system a case-only rename, such as `a` to `A`, is allowed: the new path is the file itself, not an existing file. A case-only rename of a function that has a folder of nested functions (`<name>/`) is refused with the reason, since a case-only rename cannot move the folder: rename it in two steps through another name. A destination counts as the source itself only when its path equals the source path ignoring ASCII case and it is the same file, checked without following links; a hard link or a symbolic link to the source is an existing file, so the move is refused. A rename or quick fix never sends an edit that writes the text already there. The nesting check reads the saved files on disk, so an unsaved `main.rein` in a subfolder does not count until it is saved.
- A move changes the function's path, so it changes its answer keys (section 11) and breaks a `@program/<path>` reference to it from another program. The warning says so.
- A relative reference (`@./`, `@../`) resolves only inside the same flow root. A program reference (`@program/function`) hands off to another installed program (section 4, References).
- The directory walk skips hidden directories (names starting with `.`), `target/` and `node_modules/`.
- A subdirectory with its own `main.rein` is another flow. The walk does not enter it.
- The walk follows symlinks. A symlink loop does not repeat a directory.
- A `.rein` file that cannot be read (for example, not UTF-8) is an error on that file. The file stays in the project, with empty text. The message is `cannot read file: <io error>`.
- When two sources map to the same function name, the later one wins. This applies to editor overlays only.

### 1a. Flows and scopes

Programs (flows) live in scopes: project, user, and system. The folders, the manifest, precedence, and shadowing are in [Install a program](../install-programs.md).

- `rein check <dir>`, `rein eval --root <dir>` and `rein run --root <dir>` still work on any flow root passed explicitly.
- A program is also one `.rein` file, the file form. `rein step <file.rein>`, `rein run <file.rein>` and `rein check <file.rein>` take it: the file's folder is the flow root, and the file name without `.rein` is the entry. No folder, manifest or scope is needed. Scopes and `rein list` only find programs by name.
- Imports do not exist. Relative references (`@./`, `@../`) stay inside the flow root. A program reference names another installed program.
