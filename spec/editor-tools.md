### Language server

The code is in `crates/rein/src/lsp/`, one module per feature. It reads the tree from `rein_core`'s parser and resolves references with `rein_core::project`. A relative reference cannot leave its program, so every feature below stays in one program, except workspace symbols and program references.

- Diagnostics: the checker's errors and warnings, on each open file.
- References: on a reference, on a function's name, or anywhere else in a file, every `@./` reference to that function. On a parameter or a `name=` argument, its uses and `name=` in each call to its function. On a struct type or a struct name, every parameter type that names the struct. On a field, its place in `{ }` and its uses in each function that takes the struct, and `name=` in each call to those functions. The declaration is included when the client asks for it.
- Code lens: `N references` above each function, and above a shared struct the count of parameter types that name it. Its command, `rein.showReferences`, carries the file URI, the position, and the locations.
- Go to definition: a reference goes to the name of its function. A parameter or `name=` goes to the parameter. A struct type goes to its `interface`, in the same file or in its `.struct.rein` file. A field in `{ }`, in the body, or as `name=` goes to the field in its `interface`. A std template goes to its source, which the server writes to `rein-std/` in the temp directory. `request` is built in, so it has no source.
- Call hierarchy: incoming calls are the functions that reference the function, outgoing calls are the functions it references. Each call has the spans of its references.
- Hover: on a reference or a function's name, the description and the parameters. On a parameter, a field or `name=`, its type and question. On a struct type or a struct name, its doc and its fields. On a std name, its doc.
- Rename: a parameter renames its declaration, its uses, and `name=` in each call. A field renames it in its `interface`, in `{ }` and the body of each function that takes the struct, and `name=` in each call. A function renames its file in the same folder, its folder of nested functions when it has one, the last segment of each reference, each relative reference that the folder move changes, and the name after `export default function` when it was the file name. An inline struct renames its `interface` and the parameter type. A shared struct renames its file to `<new>.struct.rein`, the last segment of each `@./` type, and its `interface` name when it was the file name. A function or shared struct rename needs a client that can rename files.
- Document symbols: the function, with its parameters and `const` answers, then each struct with its fields.
- Workspace symbols: every function of every program under the workspace folders and of the open files. A function's name is its project path. A shared struct is a struct symbol, named by its path without `.struct`. Its container is the program folder.
- Completion: after `@./` or `@../`, the project functions relative to the current file, or after `}: ` the shared structs. Each item replaces the whole reference token. Inside call parentheses, where an argument name goes, the parameters (the fields of a struct parameter) not given yet, as `name=`. After `x === "` or `case "`, the members of the union, each replacing the whole literal. Elsewhere, the parameter names, the std names, and keywords.
- Signature help: inside call parentheses, the callee's parameters (the fields of a struct parameter), with the current one active.
- Quick fixes: add a doc comment to a function or a parameter that has none, and add `name=` to a positional argument.
- Program references: `@program` and `@program/function` resolve through the scopes from the project root, as `rein check` run there resolves them. Go to definition opens the function in the installed program, or its entry for a bare `@program`. Hover adds the program name, version, scope and folder. Completion after `@` offers the visible programs, and after `@program/` the functions of that program. Signature help, `name=` completion and diagnostics read the target's parameters. References list the program references in the current program only; references from other programs are not searched. Rename refuses a symbol of another program. The scopes are searched only when the project has a `@program` reference, and a program is loaded once for the request. An open buffer of an installed program replaces its file on disk, so hover, completion and diagnostics in a hand-off see its unsaved edits. This holds when the program's folder is reached through a symlink, as pnpm links `node_modules/<name>`. An open buffer the loader would skip, such as one in a nested flow, a hidden folder, `target/` or `node_modules/`, is not a function of the program. Such a file gets no language features. Its one diagnostic is a hint at its top, which names the folder the loader does not load. Only an open buffer gets the hint: it clears when the buffer closes or the file moves. A file of an installed program, which is a folder inside the skipped folder with a `rein.json` or a `main.rein` (such as `node_modules/<name>/` or pnpm's `node_modules/.pnpm/<pkg>/node_modules/<name>/`), is a program of its own and gets no hint. Completion after `@./` or `@../` searches no scope. After `@program/` a program the file already references is read from its loaded copy.

### Debug adapter

The code is in `crates/rein/src/dap/`. `rein dap` speaks the Debug Adapter Protocol over stdio. It walks a program with the step engine (section 11), so it has no evaluator of its own. It stops at a line breakpoint on a question, a request, a hand-off, or the end. A question with no answer is sent to the client as a `rein/ask` event. The client answers with a `rein/answer` request, and the walk goes on. The editor side and the steps for the user are in the [VS Code extension README](https://github.com/rein-lang/vscode-rein#readme).
